# Data card — Firaza synthetic procurement data

## Why synthetic
Firaza did not provide vendor or procurement data (the use case document says so and allows public or synthetic data). All data here is generated by `ml/generate_data.py` with a fixed random seed (42), so anyone can regenerate exactly the same files. No personal data and no Firaza business data are used.

## Tables (`ml/data/`)

| File | Rows | Columns | Meaning |
|---|---|---|---|
| `materials.csv` | 12 | id, name, category, unit | Supplies Firaza buys: boxes, ribbon, bubble wrap, polymailer, premium hamper boxes, gift paper, embroidery thread, stickers, raffia, tape |
| `vendors.csv` | 32 | id, name, city, notes | Fictional suppliers (names built from word lists; contact names from Faker) in 8 Indonesian cities |
| `vendor_materials.csv` | 176 | id, vendor_id, material_id, unit_price, bulk_min_qty, bulk_unit_price, moq, lead_time_days, in_stock, quality_score | One vendor's offer for one material. Every material has at least 5 vendors |
| `transactions.csv` | 1,597 | id, vendor_id, material_id, qty, unit_price, ordered_at, promised_days, actual_days, defect_rate | Purchase history over the last 18 months |
| `_latent/vendor_truth.csv` | 32 | vendor_id, reliability_true, quality_true | **Hidden truth**, git-ignored, used only to create training labels |
| `ranking_train.csv` | 44,253 | request_id, split, vendor_id, 17 features, label | Learning-to-rank training table (3,000 simulated requests), git-ignored, rebuilt by `ml/build_ranking_dataset.py` |

## How the data is generated
- Each vendor has a hidden **reliability** (Beta(8,2), clipped to 0.60–0.99) and hidden **quality** (Normal(3.8, 0.5), clipped to 2.5–5).
- Prices start from a realistic base price per material and are scaled by a vendor price factor that rises slightly with quality, plus ±5% noise. Bulk prices are 8–15% lower from `bulk_min_qty = 5 × MOQ`.
- Lead times scale a base lead time per material by a vendor speed factor.
- The **observed** `quality_score` is the hidden quality plus noise (a rating is never perfect).
- A transaction is late with probability `1 − reliability` (1–4 days late); otherwise on time or one day early. Defect rates are centered on `(5 − quality)/20`.

## Deliberate data problems (so preprocessing has real work)
| Problem | Count in raw data | Fix in `clean_transactions()` |
|---|---|---|
| Duplicated entries (same order typed twice) | 15 | drop duplicates on all columns except id |
| Impossible delivery time (`actual_days` > 30) | 7 | drop the row |
| Missing `defect_rate` | 31 | vendor median, else global median |

After cleaning: 1,575 rows, 0 missing values, 0 duplicates, 0 outliers (see `ml/reports/eda_cleaning_before_after.png`).

## Features (computed by `backend/app/core/features.py`, the same code in training and in the app)
Request: `deadline_days, log_qty, w_price, w_speed, w_quality`.
Offer and history: `unit_price_eff` (bulk price if qty ≥ bulk_min_qty), `price_rel_median`, `lead_typ`, `slack_typ = deadline − lead_typ`, `lead_p90` (90th percentile of actual delivery days), `slack_p90`, `quality_score`, `ontime_rate` (smoothed toward 85% with 3 virtual orders, so vendors with little history are not over- or under-trusted), `defect_rate`, `moq_ratio = moq / qty`, `in_stock`, `n_tx`.

## Labels
For each simulated request, every candidate vendor gets a relevance grade 0–4. In plain words, the grade is high when the vendor:
- is cheap relative to the other candidates (weighted by the request's price priority),
- can deliver before the deadline and is truly reliable (weighted by the speed priority),
- has truly good quality, with diminishing returns (weighted by the quality priority),
and it is reduced when the vendor misses the deadline, when the order is below the vendor's MOQ, when the item is out of stock, and, for urgent orders (≤ 2 days), when the vendor is unreliable. A little noise is added because real judgements are not perfectly consistent. Grades are relative within each request (the best candidate tends toward 4, the worst toward 0).

The labels use the **hidden** reliability and quality. The model only sees noisy observed signals (on-time history, ratings), so it has to learn to infer the truth rather than copy a formula.

## Known limitation
**Labels derive from a function we wrote; results are prototype-level.** The evaluation shows the pipeline works and learns sensible trade-offs on simulated data. It does not prove accuracy on Firaza's real purchasing decisions. With real data, the labels would come from the owner's actual past choices or ratings.
